# 魔術言語仕様 v0.6.2

v0.6.1を基礎に、反応速度論、触媒、反応経路、可逆反応、平衡を正式化する。

## 1. 中心原則

```text
Stoichiometry != RateLaw
Kinetics != Thermodynamics
ReactionRule != ReactionPathway
Catalyst != equilibrium shift
KineticModel != Capability
Activation barrier != net reaction energy
Continuous physical time != runtime tick
```

MKI data planeは引き続き6命令であり、`REACT`, `CATALYZE`, `EQUILIBRATE` 等の新primitiveは追加しない。

```text
RESOLVE
OBSERVE
CHANNEL
TRANSFER
RECONFIGURE
CONSTRAIN
```

## 2. ReactionRuleとKineticModel

`ReactionRule` は「何が何へ変化するか」を記述する。

`KineticModel` は「その変化が、ある条件下でどの速さで進むか」を記述する。

```text
ReactionRule<R>
KineticModel<R>
```

化学量論係数だけから一般のrate lawを推論してはならない。

```text
stoichiometry ->/-> reaction order
```

高級compilerは、registryに明示されたKineticModelまたはReactionPathwayを用いる。

## 3. RateBasis

反応速度の正規化方法を型として区別する。

```text
RateBasis =
    ExtentRate
  | VolumetricRate
  | SurfaceRate
```

代表型:

```text
ReactionExtentRate
    : mol s^-1

VolumetricReactionRate
    : mol m^-3 s^-1

SurfaceReactionRate
    : mol m^-2 s^-1
```

`ReactionExtentRate` は:

```text
dξ/dt
```

である。

volumeやsurface areaを必要とするrate lawは、それらをKineticContextから明示的に受け取る。

## 4. KineticContext

rate evaluationへ渡す条件を一つのsnapshotとして扱う。

```text
KineticContext {
    composition
    thermodynamic_state
    volume?
    surface_area?
    structure?
    catalyst_state?
    fields?
    observed_at
    revision_set
}
```

KineticContextはlive world viewではない。

```text
KineticContext != live state
```

実行中に状態が変化した場合、runtimeは新しいcontextを評価してrateを更新できる。

## 5. RateLaw

一般形:

```text
RateLaw<C> {
    input_contract
    parameter_set
    valid_domain
    evaluate(context : C) -> RateEstimate
}
```

rate lawは濃度だけに限定しない。

```text
rate = f(
    activities / concentrations,
    temperature,
    pressure,
    phase,
    structure,
    catalyst_state,
    fields,
    ...
)
```

実験的rate law、elementary-step mass-action model、surface kinetics等を別modelとして登録できる。

## 6. RateEstimate

```text
RateEstimate<R> {
    value
    uncertainty
    basis
    valid_until?
    assumptions
}
```

単一の正確値を常に返せるとは仮定しない。

```text
Estimate != exact world truth
```

## 7. RateConstantModel

rate constantの温度・状態依存を別modelへ分離する。

```text
RateConstantModel {
    evaluate(context) -> RateConstantEstimate
    valid_domain
}
```

代表的な任意modelとしてArrhenius型を登録可能とする。

```text
k(T) = A exp(-Ea / (R T))
```

ここで:

```text
A  = pre-exponential factor
Ea = activation energy
R  = molar gas constant
T  = absolute temperature
```

ただしv0.6.2はすべての反応がArrhenius式に従うとは規定しない。

`A` の次元はrate lawに依存するため、一律 `s^-1` としてはならない。

## 8. ReactionPathway

同じReactionRuleを複数の経路で実現できる。

```text
ReactionPathway<R> {
    id
    overall_rule : ReactionRule<R>
    steps        : [ElementaryStep]
    kinetic_model
    catalyst_requirements
    valid_domain
    accounting_profile
}
```

```text
ReactionRule != ReactionPathway
```

例えば同じnet reactionでも、無触媒経路と触媒経路は別Pathwayになりうる。

## 9. ElementaryStep

```text
ElementaryStep {
    id
    stoichiometry
    reversible
    kinetic_model
    intermediates
    accounting_profile
}
```

elementary stepとして明示された場合のみ、registryが許すmass-action model等を係数から構成できる。

高級なoverall ReactionRuleへ同じ推論を行わない。

## 10. ReactionNetwork

複数step/pathwayが競合する系をgraph/networkとして扱う。

```text
ReactionNetwork {
    species
    steps
    pathways
}
```

各step jのextent rateを `dξ_j/dt` とすると、species i のamount変化は概念的に:

```text
dn_i/dt = Σ_j ν_i,j (dξ_j/dt)
```

となる。

したがって目的反応だけを計算して副反応を無視してよいとは限らない。

## 11. CatalystModel

触媒はReactionRuleのnet thermodynamic transformationを書き換えるものではなく、Pathway / kineticsへ作用するmodelとして扱う。

```text
CatalystModel {
    id
    requirement
    affected_pathways
    kinetic_modifiers
    state_model
    recovery_condition
    valid_domain
}
```

触媒はelementary steps内では反応物/生成物として現れてよいが、理想的なcatalytic cycleではnet stoichiometry上回収される。

```text
Catalyst participation in steps
    != net consumption in overall ReactionRule
```

触媒が実際に消耗・変質する系は、単純なideal catalystではなくactivator/reagent/deactivation等を明示する。

## 12. CatalystState

触媒性能を定数と仮定しない。

```text
CatalystState {
    activity
    occupied_sites?
    surface_state?
    poison_fraction?
    structure_revision?
}
```

`activity` はここでは触媒性能の状態量であり、thermodynamic activityとは別識別子にすることを推奨する。

## 13. InhibitorModel

反応速度を低下させるものをCatalystModelへ無理に含めず:

```text
InhibitorModel
```

として別分類可能とする。

## 14. Reversible reaction

可逆反応はforward/reverseのrateを別々に評価できる。

```text
ReversibleKineticModel {
    forward
    reverse
}
```

net extent rate:

```text
dξ_net/dt = dξ_forward/dt - dξ_reverse/dt
```

## 15. ThermodynamicActivity

平衡判定では、単純濃度だけに固定せずactivity modelを用いる。

```text
ThermodynamicActivity<SpeciesID>
ActivityModel
```

ActivityModelはstandard state、phase、非理想性等の契約を持つ。

## 16. ReactionQuotient / EquilibriumConstant

ReactionRuleのstoichiometric coefficient `ν_i` とactivity `a_i` に対し、概念的に:

```text
ReactionQuotient Qr = Π_i a_i ^ ν_i
```

平衡model:

```text
EquilibriumModel<R> {
    activity_model
    standard_state
    evaluate_K(context) -> EquilibriumConstant
    valid_domain
}
```

同一のthermodynamic convention下で:

```text
Qr ≈ K
```

となる状態をequilibriumとみなせる。

数値判定には明示的toleranceを要求する。

## 17. Dynamic equilibrium

可逆kinetic modelがthermodynamic modelと整合している場合、平衡では概念的に:

```text
forward_rate ≈ reverse_rate
net_rate ≈ 0
```

となる。

ただし「反応が停止している」ことを意味しない。

## 18. Catalystと平衡

同じoverall reaction、同じthermodynamic state / standard-state conventionでは、CatalystModelはEquilibriumConstantを書き換えない。

触媒はforward/reverseの到達速度や利用pathwayを変えうるが:

```text
Catalyst != equilibrium shifter
```

である。

系へ別species・reservoir・external workを導入した結果平衡条件が変わる場合、それは単なるcatalysisとは別のsystem definitionとしてaccountする。

## 19. Equilibrium-limited extent

PreparedReactionPlanは、指定extentがthermodynamic equilibriumにより自然には到達不能かを評価できる。

```text
EquilibriumAssessment {
    current_quotient
    equilibrium_constant
    predicted_equilibrium_extent?
    tolerance
    model_uncertainty
}
```

平衡を越えて反応を進めるには、external reservoir / Energy / matter removal等の駆動条件を明示してaccountしなければならない。

`override equilibrium` という無条件操作は用意しない。

## 20. PreparedReactionPlan拡張

```text
PreparedReactionPlan {
    rule
    pathway
    kinetic_model
    equilibrium_model?
    catalyst_requirements
    required_leases
    required_capabilities
    limiting_species

```

この構造は将来のFeasibility Evaluatorへ直接利用できる。

## 21. Energy accountingとの関係

ActivationEnergyは反応全体で消費されるEnergy量と同一ではない。

```text
Activation barrier != net Energy consumption
```

将来のEnergy estimatorは最低限:

```text
thermodynamic work / reaction energy
channel overhead
control overhead
observation/information cost
kinetic/pathway constraints
losses / efficiency
```

を分けて報告する。

v0.6.2では完全なkJ estimatorはまだ実装せず、PreparedReactionPlanへ必要情報を残せるようにする。

## 22. Kinetic feasibility

指定したdeadlineやtarget rateがある場合、PREPAREで可能性を評価できる。

概念的な結果:

```text
Feasible
ConditionallyFeasible
Infeasible
Indeterminate
```

`Indeterminate` は情報不足時の正規結果であり、無理にyes/noへ丸めない。

## 23. MIR reaction metadata

`reconfigure` に以下のoptional clauseを追加する。

```text
reconfigure target {
    reaction = @rule;
    extent = 0.5 mol;
    pathway = @pathway;
    catalyst = catalyst_ref;
    deadline = 30 s;
    identity = preserve;
}
```

- `pathway`: 使用経路を明示する。
- `catalyst`: 実際の触媒resource/entity等を渡す。
- `deadline`: planning constraintであり物理的作用そのものではない。

pathway未指定時にcompiler/runtimeが候補を選ぶ場合、選択規則・仮定・候補をFeasibility reportへ残さなければならない。

## 24. PREPARE

reaction指定時はv0.6.1の検査に加えて:

1. KineticModel availability / domain。
2. ReactionPathway availability。
3. Catalyst requirement / state。
4. RateLaw input availability。
5. equilibrium model / activity convention。
6. predicted rate / duration。
7. deadline feasibility。
8. competing pathwayを考慮する必要性。
9. uncertainty / stale context。

を検査する。

## 25. Runtime integration

v0.6.2の意味論はreaction kineticsをcontinuous physical time上のrateとして定義する。

```text
dξ/dt
```

runtimeがこれを離散tickでどう数値積分するかは、内部ティック仕様まで固定しない。

```text
continuous kinetics != runtime tick
```

実装はnumerical errorを無視してはならず、将来tick/integrator contractでtoleranceを明示する。
