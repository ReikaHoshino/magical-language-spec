# 魔術言語仕様 v0.7.2

v0.7.1を基礎に、Latin Frontendを一般化し、多言語自然言語入力を共通の正規意味表現へ変換する `LanguageAdapter` / NSR層を正式化する。

## 1. 中心原則

```text
Natural language != Semantic AST
Language-specific parse != NSR
AI proposal != semantic truth
Confidence != proof
Lexical meaning != Entity resolution
Cross-language conversion != direct translation
```

自然言語frontendはMKIを直接生成しない。各言語固有解析の後に、言語非依存かつ人間可読な `NormalizedSemanticRepresentation` (NSR) を置く。

## 2. Pipeline

```text
Natural Language Source
    ↓ LanguageAdapter<L>
SurfaceAnalysis<L>
    ↓ normalization
NormalizationCandidateSet
    ↓ AmbiguityPolicy
NormalizedSemanticRepresentation (NSR)
    ↓ deterministic semantic validation
SemanticAST
    ↓ typed elaboration
TypedMIR
    ↓ planning
KernelPlan / FeasibilityReport
```

`LanguageAdapter` はfront-end serviceであり新MKI primitiveではない。

## 3. LanguageAdapter

```text
LanguageAdapter<L> {
    adapter_id
    adapter_revision
    external_language_tags
    lexicon_revision?
    grammar_revision?
    normalization_profile
    capabilities
}
```

最低限の責務:

```text
lexical analysis
morphological analysis where applicable
syntactic / dependency analysis
semantic-role proposal
selector proposal
normalization candidate generation
source-span provenance
```

## 4. 実装優先度

project adapter IDの初期優先度:

```text
1. lat  — Latin
2. lzh  — Literary / Classical Chinese
3. ger  — German
4. jpn  — Japanese
5. eng  — English
6. zho  — Modern Chinese
```

project adapter IDとISO/BCP47等の外部tagは同一identityとして固定しない。対応はadapter metadataで管理する。

## 5. Lexicon

巨大な一般辞書をcompiler coreへ埋め込むMUST NOT。

概念的に:

```text
General Lexicon
Domain Lexicon
SemanticRegistry mappings
World / profile aliases
```

を分離する。

Domain Lexicon entry例:

```text
LexemeEntry {
    language
    lemma
    forms?
    part_of_speech?
    semantic_candidates
    verb_frame?
    register?
    provenance
}
```

lexical mappingはEntity resolutionではない。

```text
"aqua" -> semantic material hint / selector proposal
```

であり `EntityID` を直接生成しない。

## 6. AI-assisted normalization

AI/LLMをoptional normalizerとして利用MAY。

ただし:

```text
AI output = untrusted NormalizationCandidate
```

とする。

AIは候補、semantic role、omission、paraphrase等を提案できるが、TypedMIR型、Capability、EntityID、Energy値、保存則成立を権威的に決定してはならない。

AIが生成したcandidateはprovider/model/profile identityとsource spans/evidenceを記録するSHOULD。

## 7. NormalizationCandidate

```text
NormalizationCandidate {
    nsr
    evidence
    unresolved_fields
    alternatives?
    provider
    ranking_metadata?
}
```

`ranking_metadata` は証明ではない。

```text
confidence != proof
```

## 8. NSR

NSRは自然言語より抽象的、SemanticASTより人間可読な中間表現。

例:

```text
TransferCommand {
    patient = ThermalEnergy
    source = SelectorProposal("water")
    goal = SelectorProposal("air")
    quantity = Unknown(MissingSurfaceArgument)
}
```

NSRはMKI型、Capability、Lease、WorldIndex EntityIDを要求しない。

## 9. 曖昧性

```text
AmbiguityPolicy =
    StrictReject
  | InteractiveResolve
  | ContextualDeterministic
  | LegacyPermissive
```

### StrictReject

semantic-criticalな複数candidateが残れば実行候補選択を拒否。

### InteractiveResolve

人間/上位agentへcandidateを提示し選択を要求。

### ContextualDeterministic

profile-defined context/evidence/tie-breakで決定論的一意化する。選択根拠を記録するMUST。

### LegacyPermissive

古い/危険な魔術体系用。複数のsemantically valid candidateからprofile-defined規則で一つを選択MAY。

これは術者の意図と異なるが仕様上validな結果を生じうる。

```text
Unexpected result != undefined behavior
```

ただし、型/権限/保存則/mandatory safety obligationを曖昧性policyで回避してはならない。

## 10. Ambiguity provenance

選択された場合:

```text
NormalizationDecision {
    candidate_id
    policy
    evidence_used
    alternatives_rejected
    unresolved_assumptions
}
```

をreport/debug traceへ保持するSHOULD。

## 11. Cross-language normalization conversion

cross-language conversionは直接翻訳をsemantic authorityとせず、必ず共通NSRを経由する。

```text
Source<L1>
→ LanguageAdapter<L1>
→ NSR
→ SurfaceRenderer<L2>
→ Source<L2>
```

`SurfaceRenderer<L>`:

```text
SurfaceRenderer<L> {
    adapter_id
    renderer_revision
    register_profile
    fidelity_profile
}
```

rendererはNSRに存在しない新しいexecution-semantic fieldを追加してはならない。

## 12. SemanticFingerprint

```text
SemanticFingerprint(NSR)
```

をcanonical semantic contentから計算する。

fingerprintから除外する候補:

- source span。
- tokenization。
- 語順。
- morphology。
- human commentary。
- target-language-only register styling。

含める候補:

- action。
- semantic roles。
- quantities / units / Unknown marker。
- selector semantics。
- conditions / constraints。
- execution semanticsへ影響するexplicit assumptions。

具体canonicalization algorithmは次release以降でmachine-readableに定義する。

## 13. Round-trip validation

```text
N0 = normalize(source_L1)
T  = render(N0, L2)
N1 = normalize(T)

SemanticFingerprint(N0) == SemanticFingerprint(N1)
```

をsemantic round-trip successの基本条件とする。

不一致は:

```text
CrossLanguageDrift
```

として扱う。

自然言語として良い翻訳でもfingerprintが変化すれば、魔術用conversionとしてはunsafeでありうる。

## 14. Adapter-specific strategy

`lat` を最初のreference adapterとし、既存Magical Latin lexicon / verb frameを機械可読化する。

初期実装順は:

```text
lat → lzh → ger → jpn → eng → zho
```

とする。

各adapterは言語固有lexiconを持てるが、共通semantic kindはSemanticRegistryへ寄せる。

```text
language lexeme
  → semantic candidate ID
  → SemanticRegistry entry
```

同一概念を各adapter内で別々のkernel meaningとして複製しない。

FeasibilityReportは必要に応じて:

AI normalizerのconfidenceだけで `Feasible` へ昇格してはならない。

## 18. 維持する境界

```text
MKI data-plane primitives = 6
LanguageAdapter != MKI primitive
NSR != SemanticAST != TypedMIR
AI proposal != semantic truth
Confidence != proof
Lexical meaning != Entity resolution
Cross-language conversion != direct translation
Unexpected result != undefined behavior
Evaluation != Execution
WorldIndex != WorldState
Physical time != runtime tick
```

v0.7.2はfrontend/normalization層の一般化であり、既存のMKI・runtime・physics・authority modelを変更しない。
