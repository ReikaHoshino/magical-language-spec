# 魔術言語仕様 v0.6.4

v0.6.3を基礎に、`RESOLVE` / `Selection` が参照する検索データ層 **World Index** を正式化する。

## 1. 中心原則

```text
WorldIndex != WorldState
Index record != Entity
Candidate discovery != authority grant
Index visibility != full world visibility
Index snapshot != live world
```

World State `Σ` が権威ある現在状態であり、World Indexは検索用の派生viewである。

## 2. WorldIndex

概念型:

```text
WorldIndex {
    schema_revision
    index_revision
    source_world_revision
    identity_index
    symbolic_index
    spatial_index
    relation_index
    visibility_index
}
```

v0.6.4ではschemaのみ定義し、実world dataは要求しない。

## 3. WorldIndexSnapshot

Selector評価は可能な限り一つのindex snapshot上で行う。

```text
WorldIndexSnapshot {
    index_revision      : WorldIndexRevision
    source_world_revision
    captured_at         : Instant
    schema_revision
}
```

同じsnapshot、同じSelector、同じQueryContext、同じOrderSpecでのqueryは決定的である **SHOULD**。

## 4. EntityIndexRecord

```text
EntityIndexRecord<T> {
    entity_id            : EntityID<T>
    type_tags
    symbolic_names
    spatial_summary?
    relation_keys
    visibility_metadata
    record_revision
    source_world_revision
}
```

Index recordはEntity状態そのものではない。

`Ref<T>` はrecordのコピーから生成されるのではなく、候補EntityIDをauthoritative identity service/world stateで再検証して得る。

## 5. Index namespaces

最低限、論理上次を分離する。

```text
IdentityIndex
SymbolicIndex
SpatialIndex
RelationIndex
VisibilityIndex
```

実装は同一database/table群に統合してもよいが、意味責任は分離する。

## 6. SymbolicIndex

名前・aliasは一意とは限らない。

```text
"stone" -> [EntityID#A, EntityID#B, ...]
```

SymbolicSelectorは単独で暗黙のfirst matchを選んではならない。

## 7. SpatialIndex

SpatialIndexは検索用の位置summary/cacheを持てる。

高精度物理操作前には、必要precisionに応じてWorld State/OBSERVEから位置・Frameを再検証する。

```text
indexed pose != authoritative physical pose
```

## 8. RelationIndex

`owner_of`, `inside`, `attached_to`, `embodied_by` 等のrelationをquery可能にする。

relation entryにはrevision/evidence sourceを持たせるSHOULD。

## 9. QueryContext

```text
QueryContext {
    intent_context
    knowledge_context
    perception_context
    authority_context
    frame_context
    snapshot_policy
    consistency_policy
    query_budget
}
```

従来の `C=(I,K,P,A)` を包含し、index/query policyを追加した形である。

## 10. ResolverQuery

高級selectorはquery plannerにより:

```text
Selector<T>
    -> ResolverQuery<T>
    -> CandidateSet<T>
```

へ精緻化できる。

```text
CandidateSet<T> {
    candidates
    index_revision
    query_evidence
    truncated
}
```

`CandidateSet` はまだ `Ref<T>` ではない。

## 11. RESOLVE

概念フロー:

```text
Selector<T>
  -> compile ResolverQuery
  -> query WorldIndexSnapshot
  -> CandidateSet<T>
  -> visibility filtering
  -> uniqueness/type checks
  -> authoritative EntityID revalidation
  -> Ref<T>
```

単一対象が得られなければ従来通り `ResolutionFailure`。

## 12. Selection

`select<T>` はbounded CandidateSetから複数Refを生成する。

```text
Selection<T> {
    refs
    selected_at
    index_revision : WorldIndexRevision
    order
    truncated
}
```

Selectionはlive viewではない。

## 13. ConsistencyPolicy

index freshnessについて最低限:

```text
StrictSnapshot
BoundedStaleness(max_age / max_revision_lag)
BestEffort
```

を概念policyとして認める。

不可逆/危険な世界作用の対象解決では、古いindex結果だけを根拠にCOMMITしてはならない。PREPAREまたはCOMMIT直前に必要なidentity/state/authorityをauthoritative sourceで再検証する **MUST**。

## 14. Visibility / authority filtering

World Indexは全EntityIDを利用者へ漏洩するdatabaseであってはならない。

```text
queryable candidate != visible candidate
visible candidate != authorized operation
```

visibility filterは候補列挙前または結果返却前に適用できる。

存在秘匿が必要な対象は、外部へ「権限不足で存在する」と区別可能なerrorを返さないpolicyを採用できる。

## 15. Query budget

collection queryは:

```text
limit
query_budget
```

を持つ。

Index走査量、候補数、空間範囲等のbudgetを実装/World Index profileが制限できる。

## 16. Staleness

Indexが古いこととRefがstaleであることを区別する。

```text
IndexStale != StaleReference
```

Index recordが古くてもEntityが存在する場合があり、逆もありうる。

## 17. 更新モデル

World State更新からIndex反映までの方式はv0.6.4ではimplementation-defined。

例:

```text
synchronous update
event-driven update
batch update
hybrid
```

ただし実装はstaleness policyとrevision意味を文書化する **MUST**。

## 18. 新しいerror

```text
IndexUnavailable
IndexSchemaMismatch
IndexStale
QueryBudgetExceeded
IndexConsistencyFailure
```

これらは `ResolutionFailure` と区別して内部診断へ保持できる。

## 19. MKI境界

World Indexは新MKI primitiveではない。

`RESOLVE` / high-level `select` の実装が参照するresolver data serviceである。

## 20. 次版への接続

WorldIndexSnapshot revisionは、将来のdeterministic replay / runtime tick / Feasibility reportで入力依存関係として記録できる。
