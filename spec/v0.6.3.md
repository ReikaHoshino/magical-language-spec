# 魔術言語仕様 v0.6.3

v0.6.2を基礎に、仕様文書の規範語彙、許容範囲、定義責任、fail policy、文書注釈規約を正式化する。

## 1. 目的

v0.6.3は新しいMKI primitiveを追加しない。目的は、既存仕様に含まれる「適切」「十分」「必要に応じて」等の曖昧さを減らし、何が言語仕様で固定され、何がregistry/world/runtime実装へ委ねられるかを明示することである。

## 2. 規範語彙

以下を仕様上の規範語として採用する。

```text
MUST      必須。満たさない実装は当該仕様に適合しない。
MUST NOT  禁止。
SHOULD    強い推奨。逸脱には文書化された理由が必要。
SHOULD NOT 強い非推奨。採用には文書化された理由が必要。
MAY       任意。実装が選択できる。
```

日本語本文では「〜しなければならない」「〜してはならない」「〜すべき」「〜してよい」を併用できるが、規範性が重要な箇所では英大文字語を併記する。

## 3. 定義責任

仕様上の自由度を次の分類で表す。

```text
specified               この仕様で固定。
implementation-defined  実装が選ぶが、選択内容を文書化しなければならない。
registry-defined        SemanticRegistry等のtrusted registryが定義。
world-defined           世界モデル/World State contractが定義。
profile-defined         ReactionProfile等、指定profileが定義。
unspecified             複数の適合挙動が許され、選択を文書化する義務はない。
undefined               仕様が意味を与えない。安全実装は通常、事前に拒否すべき。
```

`undefined` を「何をしてもよい」という通常の低水準言語的意味では使わない。魔術言語では物理世界作用を伴うため、undefinedな世界作用へ到達する実行は原則 fail closed とする。

## 4. fail policy

次を標準とする。

```text
型・次元・payload・authority・registry契約が証明不能
    -> MUST fail closed

観測値が不確かでTruth=Indeterminate
    -> MUST NOT 暗黙にTrue/Falseへ縮約

Energy/resource estimateが一意に決まらない
    -> MUST report range / lower bound / unknown / assumptions

安全性に影響しない表示形式
    -> MAY be implementation-defined
```

## 5. tolerance / uncertainty

`tolerance`, `resolution`, `uncertainty`, numerical errorは別概念とする。

```text
tolerance   : 許容する判定/制御誤差
resolution  : 観測・表現が区別できる細かさ
uncertainty : 値についての不確かさ
numerical error : 離散化・近似計算に起因する誤差
```

これらを同一のscalarへ暗黙統合してはならない。

## 6. 許容範囲の表記

実装依存の数値は、可能なら次の形で表す。

```text
ParameterConstraint {
    lower_bound?
    upper_bound?
    tolerance?
    uncertainty?
    definition_source
}
```

`definition_source` は `specified | implementation | registry | world | profile` のいずれかを示す。

## 7. 文書注釈規約

現行reference文書は、段階的に以下のメタ情報を冒頭へ持つ。

```text
Status: normative | informative | mixed
Purpose
Non-goals
Depends on
Key invariants
Definition ownership
```

規範節と解説節が混在する場合、必要に応じて:

```text
[NORMATIVE]
[INFORMATIVE]
[RATIONALE]
[COMPATIBILITY]
```

を利用してよい。

## 8. 歴史snapshotと現行reference

`spec/vX.Y.Z.md` はその版の設計snapshotであり、後続版で意味が変更されても原則書き換えない。

`reference/` は現行版を説明するlive referenceであり、現行仕様との矛盾が見つかった場合は後続releaseで更新する。

```text
historical spec snapshot != current reference
```

## 9. 互換性の記述

型名やsyntaxが維持されていても意味契約が変わる場合、単なるsource compatibilityとsemantic compatibilityを区別する。

```text
SourceCompatible
SemanticCompatible
RegistryCompatible
RuntimeCompatible
```

安全性に関わる意味変更は、名前が同じでもcompatibleとみなしてはならない。

## 10. 現行仕様への適用

v0.6.3時点で、少なくとも以下を規範的に扱う。

- MKI data planeは6 primitiveを維持する。
- `Selector != Ref`。
- `PayloadOf<K>` はregistry contractと一致しなければならない。
- authority/Lease検査はregistry compatibilityと別である。
- `CompositionEstimate` を完全な `Composition` へ暗黙昇格しない。
- kineticsのcontinuous-time意味とruntime tick実装を分離する。
- PREPAREで証明できない安全条件は原則fail closed。

## 11. 次版への接続

この規約はWorld Index、runtime tick、Feasibility Evaluatorの各仕様で、どの部分がspecified / implementation-defined / registry-defined / world-definedかを明示する基盤とする。
