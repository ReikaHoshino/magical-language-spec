# 魔術言語仕様 v0.7.1

v0.7を基礎に、Latin Frontendまたは正規化入力をworldへ作用させず解析し、複数抽象度の解釈・必要資源・Energy・時間・権限・不確かさ・実行可能性を返す **Feasibility Evaluator / Dry-run Report Contract** を正式化する。

## 1. 中心原則

```text
Evaluation != Execution
Estimate != Reservation
Feasibility != Authority grant
Human display unit != internal SI normalization
Unknown != zero
Lower bound != expected value
Surface interpretation != Semantic AST != Typed MIR != KernelPlan
```

EvaluatorはMKI world-effect primitiveを実行しない。World Index、SemanticRegistry、world snapshot/profile等をread-only evidenceとして参照できる。

## 2. 入力

```text
EvaluationInput =
    LatinSource
  | HighLevelSource
  | SemanticAST
  | TypedMIR
  | NormalizedIR
  | StructuredInput
```

入力段階より下位の表現は生成可能な限り生成する。上位表現が存在しない入力では捏造しない。

## 3. Interpretation levels

```text
SurfaceInterpretation
SemanticAST
TypedMIR
KernelPlan
FeasibilityReport
```

各levelは前段の証拠・diagnosticへ追跡可能でなければならない。

## 4. Dry-run pipeline

```text
input
→ parse / normalize
→ semantic roles / selector extraction
→ typed elaboration
→ registry compatibility
→ read-only RESOLVE / WorldIndex evidence
→ kernel-plan expansion
→ resource / energy / timing / authority analysis
→ feasibility classification
→ report
```

`COMMIT`, physical `TRANSFER`, `RECONFIGURE`, `CONSTRAIN` registration等を実行してはならない。

## 5. KernelPlan

```text
KernelPlan {
    operations
    control_plane_requirements
    selectors
    resolved_refs?
    channels
    observations
    leases
    capabilities
    conservation_obligations
    timing_requirements
    revalidation_requirements
}
```

これは予定されたMKI/control-plane作用であり、実行済みEventではない。

## 6. Estimate<T>

数値を一意に確定できないことを第一級に扱う。

```text
Estimate<T> =
    Exact(value)
  | Range(min,max)
  | LowerBound(value)
  | UpperBound(value)
  | Distribution(summary)
  | Unknown(reason)
```

estimateは必ず、可能な限り:

```text
unit / dimension
uncertainty
assumptions
source/evidence
validity conditions
```

を持つ。

## 7. EnergyEstimate

内部正規形はEnergy意味型 + SI次元 `kg m^2 s^-2` とする。

```text
EnergyEstimate {
    total
    components {
        physical_work
        reaction_or_thermodynamic
        channel_open
        channel_maintenance
        control
        observation_information
        synchronization
        losses
        reserved_margin
    }
    accounting_boundary
    assumptions
}
```

未評価componentを0として合算してはならない。

### Human display

人間向け標準表示は原則:

```text
< 1 kJ      -> J をMAY使用
1 kJ以上    -> kJ を既定候補
非常に大    -> MJ/GJ等をMAY使用
```

ただし表示policyはprofile-defined。machine-readable reportはSI正規化値/次元を保持する。

## 8. ResourceEstimate

Energy以外にも:

```text
Momentum
Charge
MatterPayload / Species inventory
Channel count / strength / distance
observation resolution
information/control cost
Lease duration/domain
scheduler/integrator requirements
```

を報告できる。

## 9. AuthorityAssessment

```text
AuthorityAssessment {
    required_capabilities
    available_capabilities? 
    missing_capabilities
    required_leases
    conflicts?
}
```

Evaluatorが「使用可能」と判定してもCapabilityを発行しない。

## 10. ResolutionAssessment

```text
ResolutionAssessment {
    selector
    world_index_revision?
    source_world_revision?
    candidates?
    resolved_ref?
    consistency_policy
    revalidation_required
}
```

read-only dry-run resolutionは候補/Refを得てもLeaseやmutation authorityを与えない。

## 11. TimingEstimate

```text
TimingEstimate {
    channel_propagation
    predicted_execution_duration
    scheduler_assumptions
    commit_latency_bound?
    dispatch_latency_bound?
    controller_timing?
    integration_error_budget?
}
```

```text
effective_at != committed_at != resumed_at in general
```

を維持する。

## 12. Feasibility dimensions

単一boolではなく、少なくとも以下を個別評価する。

```text
syntax
semantic_typing
resolution
registry_compatibility
physics_resources
authority
lease_availability
timing
numerical_integration
conservation_identity
```

## 13. Overall status

```text
Feasible
ConditionallyFeasible
Infeasible
Indeterminate
```

規則:

- 必須条件の違反が証明された場合 `Infeasible`。
- 条件を満たせば実行可能だが、追加Capability/resource/input等が明示されている場合 `ConditionallyFeasible`。
- 必要情報不足で真偽を決定できない場合 `Indeterminate`。
- すべてのmandatory assessmentが成立し、未解決条件がない場合のみ `Feasible`。

`Unknown` estimateだけを理由に必ず`Infeasible`としてはならない。

## 14. Evidence and assumptions

```text
EvidenceRef {
    source_kind
    source_id
    revision
    field/path?
}

Assumption {
    id
    statement
    definition_source
    impact
}
```

reportは使用したRegistryHash、WorldIndexRevision、WorldRevision、runtime/scheduler/integrator profileを記録する。

## 15. Failure diagnostics

Evaluator固有diagnostic候補:

```text
EvaluationInputUnsupported
EvaluationStageUnavailable
EnergyModelUnavailable
ResourceEstimateIncomplete
MissingEvaluationEvidence
ReportSchemaMismatch
```

既存のParseError/TypeError/ResolutionFailure/AuthorityError等は、実行せず「予測されるfailure」としてreportへ格納できる。

## 16. Latin Frontend

Latin入力では最低限:

```text
source text
morphological/role interpretation
verb frame
selectors
Semantic AST
Typed MIR
KernelPlan
```

の対応を人間可読に返せる設計とする。

曖昧なLatinを都合よく補完して`Feasible`にしてはならない。曖昧性が解消できなければ既存frontend diagnosticを保持する。

## 17. Machine-readable schema

`schemas/feasibility-report.schema.json` をv0.7.1の交換形式schema骨格とする。

schemaは将来拡張を前提とし、`schema_version` を必須にする。

## 18. Syntax boundary

v0.7.1はEvaluator API/report contractを追加するが、MIR source syntaxは増やさない。

従って `grammar/mir.ebnf` の変更は不要。

## 19. v1.0への位置づけ

v0.7.1は **仕様上のdry-run契約** を定義する。

v1.0ではこれをローカル実装し、Latin/High-level/Normalized inputを実際に解析して人間可読 + machine-readable reportを返すことを目標とする。
