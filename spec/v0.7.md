# 魔術言語仕様 v0.7

v0.6.4を基礎に、continuous physical timeとruntime実装を接続する内部tick、scheduler phase、numerical integration contract、same-tick ordering、deterministic replayを正式化する。

## 1. 中心原則

```text
Physical time != runtime tick
Tick order != causal order
Execution serialization != physical causality
Event effective time != runtime commit time in general
Event commit time != continuation resume time
Integrator approximation != physical law
Deterministic replay != time rewind
TickID != user-visible time
```

runtime tickは世界の時間量子ではない。

## 2. Instant / RuntimeEpoch / TickID

既存 `Instant` はmonotonicなphysical/runtime time coordinateとして維持する。

```text
RuntimeEpochID
RuntimeTickID
```

- `RuntimeEpochID`: runtime execution session identity。
- `RuntimeTickID`: 同一epoch内で単調増加するscheduler step identity。

TickIDはdurationではなく、通常の呪文から観測可能であってはならない。

```text
now_monotonic() -> Instant
```

## 3. TickStamp / TickInterval

```text
TickStamp {
    epoch
    tick
    phase
    ordinal
}

TickInterval {
    start : Instant
    end   : Instant
}
```

```text
Δt = end - start
```

`TickStamp` はreplay/debug用runtime total orderであり、因果関係 `≺` と同一ではない。

## 4. SchedulingPolicy

最低限:

```text
FixedStep(dt)
AdaptiveStep(min_dt,max_dt,error_policy)
EventDriven
Hybrid
```

を概念policyとして認める。

採用policyはimplementation-definedだが、deterministic/replay modeではidentity/revisionを記録するMUST。

## 5. Canonical logical phases

意味上次の順序を満たすMUST。

```text
1 Ingress
2 ContinuousAdvance
3 Revalidate
4 Commit
5 PublishSnapshot
6 Control
7 IndexUpdate
8 Dispatch
```

実装はobservable semanticsを維持する範囲でphaseを統合してよい。

### Ingress

external input、scheduled task、ready continuationを取得。

### ContinuousAdvance

`[t0,t1]` 上のChannel transit、kinetics、継続processを数値的に前進。

### Revalidate

COMMIT予定targetのidentity/state revision/authority/Lease等を再検証。

### Commit

due discrete world transitionをruntimeで確定し、World State/Historyへ反映。

### PublishSnapshot

coherent post-commit WorldRevisionを公開。

### Control

Controllerがsnapshotを読み、後続actuationを計画。

### IndexUpdate

World State変更をWorld Index updaterへ通知/反映。

### Dispatch

Event通知、await continuation ready化、handler/microstep schedulingを行う。

## 6. same-tick ordering

同tick内runtime処理は:

```text
(phase,ordinal)
```

でtotal orderを持てる。

しかし:

```text
A executes before B
```

だけでは:

```text
A ≺ B
```

を意味しない。

因果edgeはEvent cause、dependency、await、必要なprogram order等から構築する。

## 7. zero-time microsteps

同一Instantで `after 0 s`、event handler等を連鎖させる場合:

```text
MicrostepOrdinal
MicrostepBudget
```

を使う。

無限zero-time chainを防ぐためMicrostepBudgetをMUST持つ。

超過:

```text
MicrostepBudgetExceeded
```

## 8. Event time model

v0.7では物理的有効時刻とruntime確定時刻を分離する。

```text
EventTimeRecord {
    effective_at : Instant
    committed_at : Instant
}
```

- `effective_at`: world model上effectが有効になる物理時刻。
- `committed_at`: runtime Commit phaseでWorld State/Historyへ確定した時刻。

exact event boundaryでは:

```text
effective_at == committed_at
```

coarse schedulingでは:

```text
|committed_at - effective_at| <= required event-time tolerance
```

をMUST満たす。

`committed_at` を過去へbackdateしてはならない。

## 9. async / TRANSFER timing

TRANSFERのmodel上の到着時刻:

```text
τ = d / v_m
effective_arrival_at = sent_at + τ
```

scheduler tick幅が `effective_arrival_at` を変更してはならない。

後続boundaryでcommitする場合:

```text
CommitLatency = committed_at - effective_arrival_at
```

を記録し、TemporalTolerance内に収める。

## 10. await / continuation timing

待機SpellInstanceの再開時刻を:

```text
resumed_at : Instant
```

とする。

```text
DispatchLatency = resumed_at - committed_at
ResponseLatency = resumed_at - effective_at
```

因果関係:

```text
Delivered(tx) ≺ continuation
```

を維持する。

## 11. TemporalTolerance

```text
TemporalTolerance {
    event_time_error?
    dispatch_latency_bound?
    synchronization_error?
    controller_jitter?
}
```

```text
TemporalTolerance != tick duration
```

粗いbaseline tickでもevent split等により厳しいtoleranceを満たせる。

## 12. numerical integration

continuous processは `IntegratorContract` を通じて近似実装する。

```text
IntegratorContract {
    id
    revision
    supported_processes
    local_error_policy
    global_error_policy?
    deterministic_profile
}
```

kineticsの規範的意味:

```text
dξ/dt = rate(context(t))
```

は変えない。

```text
Integrator approximation != physical law
```

## 13. IntegrationReport

```text
IntegrationReport {
    process_id
    interval
    integrator_id
    integrator_revision
    substeps
    estimated_local_error
    estimated_global_error?
    required_tolerance
    accepted
}
```

要求toleranceを満たせず安全継続不能なら `KineticIntegrationFailure` 等。

## 14. Controller timing

```text
ControllerTiming {
    sample_period
    max_jitter
    actuation_latency_bound
    required_phase_relation?
}
```

schedulerが満たせない場合:

```text
ControllerTimingUnsatisfied
```

## 15. Event queue / ScheduledWork

```text
ScheduledWork {
    due_at
    stable_source_id
    source_sequence
    dependencies
    priority?
}
```

同時刻かつ因果依存がないworkのtie-breakはdeterministic modeで安定していなければならない。

exact tie-break schemaはimplementation-definedだが記録するMUST。

priorityはauthorityを意味しない。

## 16. World Index synchronization

`IndexUpdate` phaseはauthoritative WorldRevisionをIndex updaterへ渡す。

World Indexが非同期更新なら:

```text
source_world_revision
WorldIndexRevision
```

の対応を記録し、v0.6.4のConsistencyPolicyを適用する。

## 17. deterministic replay

```text
ReplayManifest {
    initial_world_revision
    code_hashes
    registry_hash
    world_index_schema_revision
    scheduler_policy_id
    scheduler_policy_revision
    integrator_contracts
    deterministic_order_policy
    random_seeds
    external_input_stream_identity
}
```

Tick record:

```text
TickRecord {
    tick_id
    interval
    world_revision_before
    world_revision_after
    ingress_items
    committed_events
    integration_reports
    scheduler_decisions
    index_revision_after?
}
```

Event recordは必要に応じて `effective_at` と `committed_at` の両方を持つ。

## 18. ReplayProfile

```text
StrictDeterministic
DeterministicWithinTolerance
DiagnosticBestEffort
```

- Strict: compatible inputから同じsemantic state/Event/scheduler decision系列を要求。
- WithinTolerance: explicit numerical tolerance内の差を許容。
- BestEffort: 完全再現を保証しない診断profile。

## 19. Replay compatibility

再生可能性には少なくとも:

- code semantics/hash。
- registry contract。
- initial world state/revision。
- scheduler policy。
- integrator contract。
- deterministic order policy。
- external input / random seed。

を検査する。

開始前不一致:

```text
ReplayIncompatible
```

実行中逸脱:

```text
ReplayDivergence
```

## 20. deterministic replayとRewind

```text
DeterministicReplay != Rewind
```

Replayは別runtime/world instance上で同じ入力からexecution/historyを再構築するdebug/simulation機構。

元worldの確定済み `H` を書き換えない。

## 21. Feasibility reportへの接続

将来Evaluatorは必要に応じて:

```text
scheduler assumptions
required TemporalTolerance
predicted tick/step count range
integration error budget
controller timing requirements
CommitLatency / DispatchLatency bounds
replay compatibility metadata
```

を返せる。

## 22. 新error

```text
MicrostepBudgetExceeded
SchedulerPolicyUnavailable
TemporalToleranceUnsatisfied
ControllerTimingUnsatisfied
ReplayIncompatible
ReplayDivergence
```

## 23. Syntax boundary

`RuntimeTickID`, `TickStamp`, scheduler phaseは内部runtime metadataであり、v0.7ではMIR source syntaxへ直接公開しない。

従って既存EBNFのsyntax変更は不要。

## 24. 次の焦点

v0.7以降はFeasibility Evaluatorとmachine-readable registry/index/runtime profilesを実装可能なschemaへ近づける。
