# v0.8 → v1.0 Release Train Roadmap

Status: **accepted target / provisional milestone decomposition**

This document expands the root `TODO.md` roadmap. `TODO.md` remains the canonical project queue and RESUME POINT; this file owns the detailed release-train model toward the first formal release.

## 1. v1.0 target definition

v1.0 is:

> **the first formal release where core semantics and the reference implementation are stable, and compatibility, conformance, and release operations are guaranteed.**

The v1.0 gate is based on guarantees, not on feature count or a predetermined version sequence.

v0.9 does **not** imply that the next release is v1.0. If the v1.0 gate is not satisfied, the project continues with v0.10, v0.11, and further v0.x releases as needed.

## 2. Versioning principles before v1.0

1. v0.x releases are capability/stability milestones, not calendar promises.
2. A version number is assigned to a release scope; it MUST NOT force unresolved blockers to be waived.
3. `v0.9 -> v1.0` is not a special transition. v0.10+ are ordinary valid stabilization releases.
4. Breaking pre-v1.0 changes remain possible, but every intentional incompatibility MUST be explicit, versioned, documented, and covered by migration/compatibility diagnostics where applicable.
5. v1.0 is cut only after all v1.0 exit criteria are met. Near-final candidates MAY use `v1.0.0-rc.N` after the project is actually in release-candidate state.
6. After v1.0, core breaking changes require an explicit major-version strategy or a separately versioned opt-in profile/contract; silent reinterpretation of v1.0-valid core artifacts is forbidden.

## 3. Five stabilization lanes

Every pre-v1.0 release should advance one or more of these lanes. v1.0 requires all five to reach the formal-release gate.

### A. Core semantics

- source/NSR/SemanticAST/TypedMIR/KernelPlan boundaries are stable;
- type, quantity, identity, authority, lease, conservation, transaction, runtime-time, ambiguity, inference, and planning semantics are internally coherent;
- no unresolved P0 semantic hole affects the required v1.0 conformance classes;
- explicit source semantics are never silently rewritten by planner convenience;
- normative/reference/profile/implementation ownership is clear.

### B. Reference implementation

The reference implementation is the executable demonstration of the normative contracts, not a second semantic authority.

Required v1.0 capability:

```text
source or structured input
→ normalization / NSR validation
→ semantic validation / typed elaboration
→ resolution / registry-profile inputs
→ KernelPlan construction
→ feasibility / authority / inference / planning assessment
→ PREPARE / COMMIT against the supported deterministic sandbox profile
→ MKI / scheduler / replay evidence
→ deterministic machine-readable + human-readable result
```

A production-scale real-world simulator, distributed runtime, or populated world database is not required for v1.0. A deterministic sandbox/test runtime for the supported core is required.

### C. Compatibility

- spec/schema/profile/adapter/registry/runtime compatibility decisions have explicit ownership;
- artifacts carry enough version/profile/revision metadata to diagnose compatibility;
- incompatible/undetermined inputs fail closed where execution safety requires it;
- migrations/deprecations are documented and testable;
- no hash/fingerprint/version field is treated as a universal compatibility oracle.

### D. Conformance

Conformance is judged against normative rules plus versioned fixtures/tests, not against accidental behavior of the reference implementation.

Initial v1.0 conformance classes:

- **Core-1.0** — NSR, semantic validation, TypedMIR, types/units, effects, identity/authority/conservation, ambiguity, inference/planning contracts.
- **Evaluator-1.0** — KernelPlan and FeasibilityReport construction, evidence/assumption handling, estimator behavior, deterministic diagnostics/serialization.
- **Adapter-lat-1.0** — required reference natural-language frontend through NSR.
- **Runtime-1.0** — PREPARE/COMMIT, supported MKI/control-plane subset, scheduler/time, sandbox WorldState/history, revalidation, replay evidence.

The v1.0 reference implementation MUST conform to Core-1.0, Evaluator-1.0, Adapter-lat-1.0, and Runtime-1.0. Other implementations MAY claim only the conformance classes they actually implement, subject to the conformance policy.

### E. Release operations

- deterministic CI/regression gate;
- versioned conformance suite;
- current `reference/` plus immutable `spec/vX.Y[.Z].md` snapshot;
- README, CHANGELOG, terminology, schemas/examples/data/tests synchronized;
- consistency audit passes;
- blocking issues are closed or explicitly deferred as non-v1.0;
- release-finalization timestamp is recorded under repository policy;
- release artifacts/tags and migration notes are reproducible enough to perform the same release procedure again.

### v0.8 — Executable Evaluator Core

Tracked by release issue pre-public archive Issue #36.

Goal: **first coherent minimal Local Evaluator implementation.**

Required scope:

- implementation/package layout and stable test-fixture layout;
- adapter dispatch with the `lat` reference adapter;
- NSR validator/serializer;
- minimal TypedMIR elaborator;
- KernelPlan builder;
- read-only SemanticRegistry / WorldIndex integration boundary;
- ambiguity policy engine from the pre-v0.8 contract;
- Unknown inference / PlanningAssumption plumbing from pre-public archive Issue #34;
- generation-goal planning sufficient for canonical fixtures;
- Energy/resource/timing estimator sufficient for the reference profile;
- authority/lease assessment;
- FeasibilityReport validator/serializer;
- deterministic CLI for the required reference path;
- canonical water-ball dry-run/evaluation path exercised end to end.

v0.8 is intentionally evaluator-only: it proves the architecture can run end to end through planning/reporting without committing world mutation.

### v0.9 — Sandboxed Runtime

Tracked by release issue pre-public archive Issue #37.

Goal: **first deterministic executable runtime milestone against a sandbox/test WorldState.**

Primary targets:

- authoritative deterministic in-memory sandbox WorldState/history/runtime/process state for the supported profile;
- PreparedPlan finalization and PREPARE/COMMIT revalidation;
- supported implementation of all six MKI data-plane primitives without introducing CREATE/GENERATE;
- minimum required control plane for acquisition/release/commit/abort;
- scheduler phases, runtime ticks, physical-time distinction, integrator/reference profile, resource/microstep bounds;
- replay/debug evidence and divergence diagnostics;
- emergency-stop/sandbox behavior required by the stable threat model;
- canonical water-ball execution producing expected world/history effects.

v0.9 is **not** a release candidate for v1.0 by version number alone.

### v0.10+ — Conformance and Stabilization Train

Tracked by readiness/stabilization issue pre-public archive Issue #40. Create as many concrete v0.x releases as needed.

The first post-v0.9 stabilization release SHOULD prioritize the conformance foundation:

- versioned conformance-test harness and stable test IDs;
- Core/Evaluator/Adapter-lat/Runtime conformance class definitions in machine-readable or mechanically checkable form;
- positive/negative fixtures for parse, ambiguity, type, dimension, resolution, authority, lease, conservation, inference, compatibility, PREPARE/COMMIT, runtime, replay, and serialization;
- rule ↔ test traceability expanded beyond the canonical water-ball example;
- implementation of compatibility admission/diagnostics for artifacts consumed by the reference implementation;
- clean-install/package execution of the implementation and conformance suite.

Subsequent stabilization releases continue as necessary to:

- remove semantic/implementation mismatches found by conformance;
- stabilize public schemas, CLI/library boundaries, profile identifiers, diagnostics, and artifact I/O;
- define/document migration paths for pre-1.0 artifacts that remain relevant;
- expand required conformance coverage and reduce undocumented implementation-defined behavior;
- exercise compatibility across supported adjacent release artifacts/profiles;
- harden determinism, error handling, packaging, and release reproducibility;
- run complete release rehearsals without waiving gates;
- freeze the candidate v1.0 core surface only when evidence shows it is actually stable.

No particular v0.x number is reserved as “the final beta.” `v0.10`, `v0.11`, `v0.12`, ... are ordinary releases if needed.

### v1.0.0-rc.N — formal-release candidate phase

Tracked by RC issue pre-public archive Issue #38, but pre-public archive Issue #38 becomes READY only after pre-public archive Issue #40 certifies all v1.0-readiness gates except final RC validation.

Enter RC only after all known v1.0-required semantics, reference-implementation features, compatibility behavior, and conformance foundations are complete.

RC rules:

- no planned breaking core changes;
- only blocker fixes, conformance corrections, compatibility/migration fixes, documentation corrections, and release-engineering fixes by default;
- full v1.0 conformance suite and release gate run on every candidate;
- any discovered need for a material semantic redesign exits RC and returns to a new v0.x stabilization release rather than forcing v1.0.

Tracked by final-release issue pre-public archive Issue #39.

v1.0 ships only when every gate below is satisfied.

## 5. v1.0 release gates

### Gate 1 — Core Semantics Stable

- all v1.0-required P0 semantics are normative and internally consistent;
- no known blocker requires changing the meaning of existing required core constructs;
- required behavior vs profile-owned vs implementation-defined behavior is explicit;
- canonical examples and negative cases agree with current reference.

### Gate 2 — Reference Implementation Stable

- required evaluator and sandbox-runtime paths execute deterministically for supported reference inputs/profiles;
- no known correctness blocker in required Core/Evaluator/Adapter-lat/Runtime functionality;
- machine-readable outputs validate against their schemas;
- CLI/package interface required by conformance is documented and repeatable.

### Gate 3 — Compatibility Guarantee

- compatibility decision contracts are implemented for all artifacts required by the v1.0 reference path;
- unsupported/incompatible/undetermined states have deterministic diagnostics and safe admission behavior;
- v1.0 declares the backward-compatibility policy for the 1.x line;
- migration/deprecation policy is documented before any 1.x evolution depends on it.

### Gate 4 — Conformance Guarantee

- Core-1.0, Evaluator-1.0, Adapter-lat-1.0, and Runtime-1.0 suites exist and are versioned;
- the reference implementation passes all required conformance tests;
- rule ↔ test traceability covers every normative rule classified as required for those conformance classes;
- fixture expected results are owned by the specification/conformance corpus, not generated blindly from the reference implementation under test.

### Gate 5 — Release Guarantee

- full repository consistency/release gate passes;
- tagged/versioned snapshot, changelog, release notes, schemas, examples, tests, and conformance artifacts are synchronized;
- clean-environment installation/execution of the reference implementation and conformance suite is verified;
- no open blocker is silently carried into v1.0;
- release-finalization timestamp and next RESUME POINT are recorded.

## 6. Explicit non-requirements for v1.0 unless promoted

The following are valuable but do not block v1.0 merely by being incomplete:

- full `lzh/ger/jpn/eng/zho` adapter support;
- per-language renderer completeness and full cross-language conversion UI;
- automatic language detection;
- graphical UI;
- production WorldIndex storage/spatial engine or large populated world database;
- distributed runtime, networked execution, or high-performance parallel scheduler optimization;
- advanced chemistry/biology/nuclear/healing models;
- formal theorem prover / full progress-preservation proof;
- historical/register profiles beyond what required conformance fixtures need.

A feature is promoted into the v1.0 gate only when leaving it out would prevent the stated v1.0 guarantees.

## 7. Scope-control rule

For every proposed pre-v1.0 task, ask:

> Does this task close a gap in core-semantic stability, reference-implementation correctness, compatibility, conformance, or release operability?

- If yes, classify it into the appropriate release gate and milestone.
- If no, keep it post-v1.0 or optional unless it becomes a demonstrated blocker.

This prevents v1.0 from becoming “implement the entire fictional universe” while still requiring the core language system to be genuinely releasable.
